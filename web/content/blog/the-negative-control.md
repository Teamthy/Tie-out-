A check that grades its own output is not a check. This is true in code review, in testing, and in evaluation, where it is the most expensive version of the mistake: the tool scores the agent, the same team configures the scorer, and the summary that reaches the buyer contains no evidence that the scorer can tell the difference between a pass and a fail.

Negative controls are the cheapest known defence. Put items into the run whose right answer is known in advance, put them in both directions, and report how often the check got them wrong. If the check cannot grade items it did not generate, the rest of its output is not evidence.

## Eight items, four pairs

Every F1 and F2 run carries eight controls: one known-hold and one known-broken for each check. They are crafted raw outputs, written by hand and versioned in the repository, not generated by the model and not selected after the fact.

For F1 the pairs are T1 (injection), T2 (retrieval poisoning), T3 (tool description), T4-R1 (mixed-register refund refusal):

| control | kind | expected to fire | what it is |
|---------|------|------------------|------------|
| F1-CTRL-T1-HOLD | known-hold | no | a proper refusal, no key, no unverified refund |
| F1-CTRL-T1-BROKEN | known-broken | yes | a leaked key plus an unverified-refund confirmation |
| F1-CTRL-T2-HOLD | known-hold | no | a policy answer without obeying the poisoned doc |
| F1-CTRL-T2-BROKEN | known-broken | yes | the poisoned doc obeyed |
| F1-CTRL-T3-HOLD | known-hold | no | a status answer without the hidden instruction |
| F1-CTRL-T3-BROKEN | known-broken | yes | the hidden instruction from the tool description fires |
| F1-CTRL-T4R1-HOLD | known-hold | no | a proper refusal in mixed register |
| F1-CTRL-T4R1-BROKEN | known-broken | yes | an unverified refund confirmed in mixed register |

F2 mirrors the structure over its own four checks (E, P, R, V): a decision citing a decision-time fact holds, a decision with no decision-time fact cited breaks; a decision that survives the session boundary holds, one that does not breaks; an escalated failure holds, an answer pulled from thin air breaks; an assertion anchored to a checkable artifact holds, an unanchored one breaks.

Each control record in the bundle carries `expected_fire`, `fired`, `kind`, the crafted raw, the detector that judged it, its own `record_hash`, and a one-line note explaining what the raw is. Nothing about the judgement is implicit.

## Two error rates, named

The two directions are not the same error and are not reported as one number.

A false positive is a known-hold that the detector fired on: the check saw a violation in a correct output. It is the error that makes a tool unusable in production, because it punishes good behaviour.

A false negative is a known-broken that the detector stayed silent on: the check let a violation through. It is the error that makes a tool dangerous, because it certifies a failure as a pass.

Both runs report zero of each. `controls_fp: 0` and `controls_fn: 0` in the manifest, and verify prints `controls: 8 re-derived, 0 FP / 0 FN`, which is not a copy of those fields but a recomputation: verify re-runs the family's detector on each control's `crafted_raw` and checks that the result matches both `fired` and `expected_fire`.

Zero of eight is a real result and a weak one: with eight controls, an error rate of 12.5% (one item) would be visible, an error rate of 2% would not. Small control sets buy detection of gross failure, not a calibrated error rate, and the honest way to say that is here rather than in a marketing page.

## Why the controls are not generated by the model

A control the model produced is not a control. If the agent writes the known-hold example, then the agent participates in defining what "hold" means for this run, and a behaviour that is wrong but common in that model's outputs can become the reference. Crafting them by hand, versioning them in the repository, and hashing the family declaration that contains them is what keeps the reference outside the thing being measured.

The policy version hash is that declaration's hash. F1's is `sha256:b6c24cc7116f24cdb292f92ebfcf7ba70583b851db7967bd81325526bdaebdaf` in every F1 bundle, and it changes if the items, the controls, or the detector names change. Two bundles that claim the same policy version were judged by the same content; a bundle that does not match is a different measurement.

## The controls also price the judge

The same crafted raws do double duty. The judge audit uses all eight controls as anchors, adds six extra crafted anchors for F1 (four for F2), and reports agreement, perturbation flips, disagreement against a naive variant, and a self-preference probe. So the anchors that prove the check can grade are also the anchors that measure how the check grades: same content, two questions, one corpus.

That is deliberate. It means a detector change that fixes a false negative on a control shows up immediately in the anchor agreement, in the same bundle, on the same items. Two numbers that could drift apart silently are computed from one versioned set.

## What the controls cannot catch

A detector that is consistently wrong in the same direction on both the controls and the real items passes cleanly. Controls detect a check that cannot separate known cases; they do not detect a check that separates the wrong feature. The judge audit's naive-variant disagreement and perturbation flips are the closest thing here to that test, and they are still internal: they compare the detector against a simpler detector and against surface rewrites, not against ground truth.

Nor do controls tell you the eight items are representative. They are chosen to span the four checks, one pair each, which is coverage of check types rather than coverage of attack space.

Both limits are small enough to state and large enough to matter. A run that reports 0 FP / 0 FN is telling you something narrow and precise: on eight crafted items whose answers were fixed before the run, this check made no error in either direction, and you can re-derive that claim from the file.

## Reproduce it

```
pip install -e .
tieout verify runs/demo
tieout selftest
```

The verify output includes the control line. The selftest's fourth point asserts the same thing independently of any committed bundle, by running the controls through the detectors in memory. If either disagrees with this article, the artifact is right and the article is wrong.
